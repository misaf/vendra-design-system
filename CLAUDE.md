# Vendra Design System — working rules

1. **Templates are the source of truth.** `templates/storefront-*` is the only maintained storefront. Keep page copy, behavior and styles with each template; shared examples and helpers live under `templates/`.
2. **Maintain shared storefront code in `templates/_shared/`.** Header, footer, menu and layout markup have their own HTML files; `routing.js` owns URL helpers, `navigation.js` owns shell/menu values, `page-lifecycle.js` owns responsive state/focus/SEO, `seo.js` (`AG_SEO`: route parsing, `<head>`, JSON-LD) and `page-focus.js` (`AG_NAV`) load in every page head before the shared logic, and `formatting.js` wraps number/currency formatting; `catalog.js` owns sample products and `delivery.js` owns delivery rules. Run `npm --prefix templates run build` after editing shared files or template classes. Install the locked Tailwind development dependencies with `npm --prefix templates ci` on first setup. Use `npm --prefix templates run dev` for Vite preview with automatic rebuilds. Runtime assets are shared from `templates/_runtime/`; do not duplicate runtime JS or CSS in page folders. Page-specific `logic.js`, `copy.js` and `styles.css` are maintained sources, compiled/generated into the shared runtime and HTML. Never edit generated sections in a page. Page markup stays in the marked editable regions of each `Storefront*.dc.html`; page behavior lives in adjacent `logic.js` and regenerates into `GENERATED PAGE LOGIC`. Bilingual page copy lives in each page folder’s `copy.js` and regenerates into `GENERATED PAGE COPY`; Use Tailwind utilities first for storefront presentation; custom page CSS is reserved for contextual/component exceptions in adjacent `styles.css` and builds into one shared runtime stylesheet. Genuinely shared translations stay in `_shared/translations/`. See `templates/README.md`; verify with `npm --prefix templates run check` and `npm --prefix templates test`.
3. **One folder per component.** `components/<Name>/` holds `<Name>.jsx`, `<Name>.d.ts`, `<Name>.css` (its `.ag-*` classes; add it to `components/index.css`) and `README.md`; only a tightly bound part (like `ChoiceGroup/ChoiceTile.jsx`) shares a folder. Build class names with `cx()` and form controls on `Field` (`useField`, `FieldMessage`). Code is formatted by Prettier: run `npm --prefix templates run format`; `check` fails otherwise. `npm --prefix templates run build` compiles every `.js`/`.jsx` under `components/` into `templates/_runtime/components.js` (generated by `templates/_build/components.cjs`; never edit it). Sources import React as a default (`import React from 'react'`), import each other by name with relative paths, and export with `export function`/`export const`; the build refuses anything else. The same build writes `dist/`, the `@vendra/design-system` package tenant storefronts install (ES modules + `.d.ts`, `styles.css`, tenant CSS, the theme API); never edit it, and keep it committed. Every exporting source needs a sibling `.d.ts`, must server-render without `window` at import time, and must take tenant data (copy, prices, currency, contact) as props, never hard-code it. Scratch scripts, generators, sample data and storefront-only helpers stay out of `components/` (those helpers live in `templates/_shared/`). Package helpers go in `components/utils/`. Never put a second React/Babel copy outside `templates/_vendor/`.
4. **Tenant themes must pass contrast.** Tenant themes are `tokens/tenants/*.json`; `npm --prefix templates run build` generates the matching `.css` (never edit it). Any new or changed tenant must pass all seven Theme builder checks (`guidelines/theme-builder.html`) and the Colors → Contrast card with `data-tenant` set, per `guidelines/tenant-onboarding.md`. Report results before calling it done.
5. **Check the cards after significant changes.** After edits to components, their CSS, tokens or `styles.css`, run `npm --prefix templates run build`, then `npm --prefix templates run test:e2e` (every @dsCard card in `guidelines/` and storefront view is screenshot-compared, with axe checks; it uses the installed Google Chrome). Look at any failing card's `-actual.png` before accepting it with `test:e2e:update`, and fix breakage before finishing.
