# Vendra Design System — working rules

1. **Templates are the source of truth.** `templates/storefront-*` is the only maintained storefront. Keep page copy, behavior and styles with each template; shared examples and helpers live under `templates/`.
2. **Maintain shared storefront code in `templates/_shared/`.** Header, footer, menu and layout markup have their own HTML files; `routing.js` owns URL helpers, `navigation.js` owns shell/menu values, `page-lifecycle.js` owns responsive state/focus/SEO, `seo.js` (`VF_SEO`: route parsing, `<head>`) and `page-focus.js` (`VF_NAV`) load in every page head before the shared logic, and `formatting.js` wraps number/currency formatting; `catalog.js` owns sample products and `delivery.js` owns delivery rules. Run `npm --prefix templates run build` after editing shared files or template classes. Install the locked Tailwind development dependencies with `npm --prefix templates ci` on first setup. Use `npm --prefix templates run dev` for Vite preview with automatic rebuilds. Runtime assets are shared from `templates/_runtime/`; do not duplicate runtime JS or CSS in page folders. Page-specific `logic.js`, `copy.js` and `styles.css` are maintained sources, compiled/generated into the shared runtime and HTML. Never edit generated sections in a page. Page markup stays in the marked editable regions of each `Storefront*.dc.html`; page behavior lives in adjacent `logic.js` and regenerates into `GENERATED PAGE LOGIC`. Bilingual page copy lives in each page folder’s `copy.js` and regenerates into `GENERATED PAGE COPY`; Use Tailwind utilities first for storefront presentation; custom page CSS is reserved for contextual/component exceptions in adjacent `styles.css` and builds into one shared runtime stylesheet. Genuinely shared translations stay in `_shared/translations/`. See `templates/README.md`; verify with `npm --prefix templates run check` and `npm --prefix templates test`.
3. **One folder per component.** `components/<Name>/` holds `<Name>.jsx`, `<Name>.d.ts`, `<Name>.css` (its `.ag-*` classes; add it to `components/index.css`) and `README.md` (a component that only reuses existing classes — `.ag-input` from `Field.css`, `.ag-check` from `Checkbox.css`, `.ag-sr-only`/`.ag-flip-rtl` from `tokens/base.css` — has no `.css`); only a tightly bound part (like `ChoiceGroup/ChoiceTile.jsx`) shares a folder. Build class names with `cx()` and form controls on `Field` (`useField`, `FieldMessage`). All code in `components/` and `templates/` (except generated files, vendored code and HTML pages) is formatted by Prettier: run `npm --prefix templates run format`; `check` fails otherwise. Use descriptive names (`fieldId`, `onKeyDown`, `selectedId`), not abbreviations. Prefixes say where a name comes from: `ag-` classes and `AG_*` globals (`AG_FORMAT`, `AG_DATES`, `AG_COMMERCE`) belong to the package in `components/`; `vf-` classes, `VF_*` globals and `vf*` functions belong to the Vendra Florist templates. One name per global, no aliases. `npm --prefix templates run build` compiles every `.js`/`.jsx` under `components/` into `templates/_runtime/components.js` (generated by `templates/_build/components.cjs`; never edit it). Sources import React as a default (`import React from 'react'`), `react-aria-components` and `@internationalized/date` by name (interactive components are built on React Aria Components; `templates/_build/vendor.cjs` bundles only the imported names into the runtime, and the package lists them as exact-version dependencies matching `templates/package.json`), import each other by name with relative paths, and export with `export function`/`export const`; the build refuses anything else. Helpers (`format`, `dates`, `commerce`) import nothing. The same build writes `dist/`, the `@vendra/design-system` package tenant storefronts install (ES modules + `.d.ts`, `styles.css`, tenant CSS, the theme API); never edit it, and keep it committed. Every exporting source needs a sibling `.d.ts`, must server-render without `window` at import time (touch `window`/`document` only inside effects and event handlers), and must take tenant data (copy, prices, currency, contact) as props, never hard-code it. Scratch scripts, generators, sample data and storefront-only helpers stay out of `components/` (those helpers live in `templates/_shared/`). Package helpers go in `components/utils/`; storefront rules that a tenant app also needs (delivery, totals, discounts, API adapters) go in `components/utils/commerce.js` as pure functions taking the tenant's data, and `templates/_shared/` only passes the sample store's data to them. Never put a second React/Babel copy outside `templates/_vendor/`.
4. **Tenant themes must pass contrast.** Tenant themes are `tokens/tenants/*.json`; `npm --prefix templates run build` generates the matching `.css` (never edit it). Any new or changed tenant must pass all seven Theme builder checks (`guidelines/theme-builder.html`) and the Colors → Contrast card with `data-tenant` set, per `guidelines/tenant-onboarding.md`. Report results before calling it done.
5. **Check the cards after significant changes.** After edits to components, their CSS, tokens or `styles.css`, run `npm --prefix templates run build`, then `npm --prefix templates run test:e2e` (every @dsCard card in `guidelines/` and storefront view is screenshot-compared, with axe checks; it uses the installed Google Chrome). Look at any failing card's `-actual.png` before accepting it with `test:e2e:update`, and fix breakage before finishing.
