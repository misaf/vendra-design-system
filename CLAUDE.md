# Vendra Design System — working rules

1. **Templates are the source of truth.** `templates/storefront-*` is the only maintained storefront. Keep page copy, behavior and styles with each template; shared examples and helpers live under `templates/`.
2. **Maintain shared storefront code in `templates/_shared/` and the app in `templates/app/`.** The storefront is a Vite React app: `app/index.html` → `app/main.jsx` renders the click-through site (`storefront-site`) or one page with `?page=<name>`. `app/Shell.jsx` holds the header, footer, mobile menu, consent and tab bar; `app/runtime.jsx` hosts page logic (`definePage`, `DCLogic`, `VFPage`); `app/ds.js` re-exports the components from `components/`. Each `storefront-*` folder holds `View.jsx` (the page's JSX inside `Shell`, reading `v`), `logic.js` (state, lifecycle, `renderVals()`), `copy.js` (bilingual copy, `vfCopy`), `styles.css` and `Page.jsx`. In `_shared/`, `routing.js` owns URL helpers, `navigation.js` owns shell/menu values, `page-lifecycle.js` owns responsive state/focus/SEO, `seo.js` (`VF_SEO`) and `page-focus.js` (`VF_NAV`) load before the shared logic, `formatting.js` wraps number/currency formatting, `catalog.js` owns sample products and `delivery.js` owns delivery rules — all ES modules that import what they use (only `seo.js` and `page-focus.js` stay classic scripts loaded by `app/index.html`). Run `npm --prefix templates run build` after editing shared files, components or template classes. Install with `npm ci` at the repo root on first setup: `templates` is an npm workspace of the root package, so there is one lockfile and one `node_modules` (React pinned to 18.3.1 there). Use `npm --prefix templates run dev` for the Vite preview. Runtime assets in `templates/_runtime/` are generated; never edit them. Use Tailwind utilities first for storefront presentation; custom page CSS is reserved for contextual/component exceptions in the page's `styles.css` and builds into one shared runtime stylesheet. Genuinely shared translations stay in `_shared/translations/`. See `templates/README.md`; verify with `npm --prefix templates run check` and `npm --prefix templates test`.
3. **One folder per component.** `components/<Name>/` holds `<Name>.jsx`, `<Name>.d.ts`, `<Name>.css` (its `.ag-*` classes; add it to `components/index.css`) and `README.md` (a component that only reuses existing classes — `.ag-input` from `Field.css`, `.ag-check` from `Checkbox.css`, `.ag-sr-only`/`.ag-flip-rtl` from `tokens/base.css` — has no `.css`); only a tightly bound part (like `ChoiceGroup/ChoiceTile.jsx`) shares a folder. Build class names with `cx()` and form controls on `Field` (`useField`, `FieldMessage`). All code in `components/` and `templates/` (except generated files, vendored code and HTML pages) is formatted by Prettier: run `npm --prefix templates run format`; `check` fails otherwise. Use descriptive names (`fieldId`, `onKeyDown`, `selectedId`), not abbreviations. Prefixes say where a name comes from: `ag-` classes and `AG_*` globals (`AG_FORMAT`, `AG_DATES`, `AG_COMMERCE`) belong to the package in `components/`; `vf-` classes, `VF_*` globals and `vf*` functions belong to the Vendra Florist templates. One name per global, no aliases. `npm --prefix templates run build` compiles every `.js`/`.jsx` under `components/` into `templates/_runtime/components.js` (generated by `templates/_build/components.cjs`; never edit it). Sources import React as a default (`import React from 'react'`), `react-aria-components` and `@internationalized/date` by name (interactive components are built on React Aria Components; `templates/_build/vendor.cjs` bundles only the imported names into the runtime, and the package lists them as exact-version dependencies), import each other by name with relative paths, and export with `export function`/`export const`; the build refuses anything else. Helpers (`format`, `dates`, `commerce`) import nothing. The same build writes `dist/`, the `@vendra/design-system` package tenant storefronts install (ES modules + `.d.ts`, `styles.css`, tenant CSS, the theme API); never edit it, and keep it committed. Every exporting source needs a sibling `.d.ts`, must server-render without `window` at import time (touch `window`/`document` only inside effects and event handlers), and must take tenant data (copy, prices, currency, contact) as props, never hard-code it. Scratch scripts, generators, sample data and storefront-only helpers stay out of `components/` (those helpers live in `templates/_shared/`). Package helpers go in `components/utils/`; storefront rules that a tenant app also needs (delivery, totals, discounts, API adapters) go in `components/utils/commerce.js` as pure functions taking the tenant's data, and `templates/_shared/` only passes the sample store's data to them. Never put a second React/Babel copy outside `templates/_vendor/`.
4. **Tenant themes must pass contrast.** Tenant themes are `tokens/tenants/*.json`; `npm --prefix templates run build` generates the matching `.css` (never edit it). Any new or changed tenant must pass all seven Theme builder checks (`guidelines/theme-builder.html`) and the Colors → Contrast card with `data-tenant` set, per `guidelines/tenant-onboarding.md`. Report results before calling it done.
5. **Check the cards after significant changes.** After edits to components, their CSS, tokens or `styles.css`, run `npm --prefix templates run build`, then `npm --prefix templates run test:e2e` (every @dsCard card in `guidelines/` and storefront view is screenshot-compared, with axe checks; it uses the installed Google Chrome). Look at any failing card's `-actual.png` before accepting it with `test:e2e:update`, and fix breakage before finishing.
