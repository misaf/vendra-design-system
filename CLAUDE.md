# Vendra Design System — working rules

1. **Templates are the source of truth.** `templates/storefront-*` is the only maintained storefront. Keep page copy, behavior and styles with each template; shared examples and helpers live under `templates/`.
2. **Maintain shared storefront code in `templates/_shared/` and the app in `templates/app/`.** The storefront is a Vite React app: `app/index.html` → `app/main.jsx` renders the click-through site (`storefront-site`) or one page with `?page=<name>`; `app/pages.js` loads each page as its own chunk on demand (the site preloads the rest when idle). `app/Shell.jsx` holds the header, footer, mobile menu, consent and tab bar; `app/runtime.js` loads the integrations and the tenant theme; `app/ds.js` re-exports the components from `components/`. Each `storefront-*` folder holds `View.jsx` (the page's JSX inside `Shell`, reading `v`), `logic.js` (the `usePage(props)` hook, on `usePageLogic`/`useLifecycle` from `_shared/page-state.js` and `useStorefrontPage`), `copy.js` (bilingual copy, `vfCopy`), `styles.css` and `Page.jsx` (a function component). In `_shared/`, `routing.js` owns URL helpers, `navigation.js` owns shell/menu values, `page-lifecycle.js` owns responsive state/focus/SEO, `seo.js` (`VF_SEO`) and `page-focus.js` (`VF_NAV`) hold the SEO and focus helpers, `formatting.js` wraps number/currency formatting, `catalog.js` owns sample products and `delivery.js` owns delivery rules — all ES modules that import what they use. Run `npm --prefix templates run build` after editing shared files, components or page logic. Install with `npm ci` at the repo root on first setup: `templates` is an npm workspace of the root package, so there is one lockfile and one `node_modules` (React pinned to 18.3.1 there). Use `npm --prefix templates run dev` for the Vite preview. Runtime assets in `templates/_runtime/` are generated; never edit them. Use Tailwind utilities first for storefront presentation; custom page CSS is reserved for contextual/component exceptions in the page's `styles.css` and builds into one shared runtime stylesheet. Genuinely shared translations stay in `_shared/translations/`. See `templates/README.md`; verify with `npm --prefix templates run check` and `npm --prefix templates test`.
3. **One folder per component.** `components/<Name>/` holds `<Name>.jsx`, `<Name>.d.ts`, `<Name>.css` (its `.ag-*` classes; add it to `components/index.css`), `README.md`, and its browser test: `<Name>.spec.mjs` with `<Name>.fixture.jsx` (see `templates/README.md` → Component tests; `npm test` fails without them) (a component that only reuses existing classes — `.ag-input` from `Field.css`, `.ag-check` from `Checkbox.css`, `.ag-sr-only`/`.ag-flip-rtl` from `tokens/base.css` — has no `.css`); only a tightly bound part (like `ChoiceGroup/ChoiceTile.jsx`) shares a folder. Build class names with `cx()` and form controls on `Field` (`useField`, `FieldMessage`). All code in `components/` and `templates/` (except generated files, vendored code and HTML pages) is formatted by Prettier: run `npm --prefix templates run format`; `check` fails otherwise. Use descriptive names (`fieldId`, `onKeyDown`, `selectedId`), not abbreviations. Prefixes say where a name comes from: `ag-` classes and `AG_*` globals (`AG_FORMAT`, `AG_DATES`, `AG_COMMERCE`) belong to the package in `components/`; `vf-` classes, `VF_*` globals and `vf*` functions belong to the Vendra Florist templates. One name per global, no aliases. Components are ES modules: they import React as a default (`import React from 'react'`), `react-aria-components` and `@internationalized/date` by name (interactive components are built on React Aria Components; the package lists them as peer dependencies, ranges starting at the exact versions pinned here, so an app shares one copy; its router and locale reach the components through `VendraProvider`), import each other by name with relative paths, and export with `export function`/`export const`. The storefront app and the guideline cards import the sources directly (cards through `guidelines/card-runtime.js`, which sets the `window.VendraDesignSystem` namespace their `.card.jsx` scripts read); Vite compiles them. Helpers (`format`, `dates`, `commerce`) import nothing. `npm --prefix templates run build` writes `dist/`, the `@vendra/design-system` package tenant storefronts install (ES modules + `.d.ts`, `styles.css`, tenant CSS, the theme API); never edit it, and keep it committed. Every exporting source needs a sibling `.d.ts`, must server-render without `window` at import time (touch `window`/`document` only inside effects and event handlers), and must take tenant data (copy, prices, currency, contact) as props, never hard-code it. The package CSS is in cascade layers (`vendra.tokens`, `vendra.base`, `vendra.components`, declared in `styles.css`); the storefront loads Tailwind first and puts its page CSS in `vendra.components` (`_build/custom-css.cjs`), so specificity between page CSS and components works as written. A component's own built-in wording (accessible names, small labels) goes in `components/utils/messages.js` in English and Persian and is read with `useMessages`, never as an English default prop; `VendraProvider` picks the language. Scratch scripts, generators, sample data and storefront-only helpers stay out of `components/` (those helpers live in `templates/_shared/`). Package helpers go in `components/utils/`; storefront rules that a tenant app also needs (delivery, totals, discounts, API adapters) go in `components/utils/commerce.js` as pure functions taking the tenant's data, and `templates/_shared/` only passes the sample store's data to them. There is one React install, at the repo root; never add another copy.
4. **Tenant themes must pass contrast.** Tenant themes are `tokens/tenants/*.json`; `npm --prefix templates run build` generates the matching `.css` (never edit it). Any new or changed tenant must pass all seven Theme builder checks (`guidelines/theme-builder.html`) and the Colors → Contrast card with `data-tenant` set, per `guidelines/tenant-onboarding.md`. Report results before calling it done.
5. **Check the cards after significant changes.** After edits to components, their CSS, tokens or `styles.css`, run `npm --prefix templates run build`, then `npm --prefix templates run test:e2e` (every @dsCard card in `guidelines/` and storefront view is screenshot-compared, with axe checks, and every component's own spec runs; it uses the installed Google Chrome). Look at any failing card's `-actual.png` before accepting it with `test:e2e:update`, and fix breakage before finishing. CI (`.github/workflows/ci.yml`) runs the same suites in Playwright's Linux image against the `-linux.png` baselines; after an intended visual change, refresh those with the **Update screenshots** workflow (see `templates/README.md`).
